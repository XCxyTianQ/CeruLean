## 1. 我们的现状（C2 事实 + 实测线程清单）

### 1.1 接线事实

| 项 | 现状 | 位置 |
|---|---|---|
| 区块→拓扑 | `BaseChunkSystemHooks.onChunkHolderCreate/Delete` → `CeruLeanRegions.addChunk/removeChunk` | `cerulean-server/minecraft-patches/features/0001-*.patch` |

## 3. concurrentutil 调度引擎（Folia 的调度其实是"用库"，不是自己写的）

**最重要的发现**：Folia 的 `TickRegionScheduler` 自己**不实现线程池与调度算法**，而是委托给
`ca.spottedleaf.concurrentutil`：

```java
import ca.spottedleaf.concurrentutil.scheduler.EDFSchedulerThreadPool;
import ca.spottedleaf.concurrentutil.scheduler.StealingScheduledThreadPool;
import ca.spottedleaf.concurrentutil.scheduler.Scheduler;
import ca.spottedleaf.concurrentutil.scheduler.SchedulableTick;
```

### 3.1 调度契约（`Scheduler` / `SchedulableTick`）

- `SchedulableTick` 是**自调度**对象：`runTick()` 返回 true = 还要被调度，但**必须自己调 `setScheduledStart(next)`**；
  返回 false = 停止调度。（SchedulableTick.java:L31-L39）
- 四个钩子：`runTick()`、`hasTasks()`、`runTasks(BooleanSupplier canContinue)`、`id()`。
- **同一个 tick 实例不可重复 schedule**：`SchedulableTick.setState` 是 `synchronized(this)` 且只允许
  `null → 非 null` 一次；Folia 靠 `copy()` 产生新实例来重新调度（SchedulableTick.java:L16-L25；TickRegions.java:L114-L117）。
- `runTick` 与 `runTasks` **保证不会并行**（库的类注释）。
- `notifyTasks()` 只是"该 tick 有中间任务可跑"的提示，不排新 tick（Scheduler.java:L18-L22）。

### 3.2 EDF 线程池（`EDFSchedulerThreadPool`，546 行真实源码）

- 纯 EDF：`LinkedSortedSet awaiting`（放"该线程正在等的那一个 tick"）+ `PriorityQueue queued`（待认领）；
  比较器 = `TimeUtil.compareTimes(scheduledStart)`，平手用 id（EDF:L20-L29）。
- **每线程只挂一个 deadline**：`insertFresh` 在无空闲线程时，若新 tick 比 `awaiting.last()` 更早，
  就踢掉尾巴、把被踢者丢进 `queued`（EDF:L145-L166）。
- 线程态：`IDLE` → `LockSupport.park()`；`AWAITING_TICK` → `parkNanos(blocker, deadline - now)` 睡到点（EDF:L424-L451）。
- 跨线程状态只在 `scheduleLock` 内改；**只有 runner 自己**能把状态升到 `EXECUTING_TICK`，且在锁内二次校验（EDF:L384-L394）。
- **不支持 NUMA**（类注释明写）；**不支持中间任务**（`notifyTasks` 空实现，EDF:L274-L276 + "Not implemented"）。
- 过载 = 排队 + deadline 顺延；没有准入控制、没有丢弃。

### 3.3 工作窃取池（`StealingScheduledThreadPool`，1156 行真实源码）

- 每线程两条 `ConcurrentSkipListMap`：`tickQueue`（按 `atNS`）与 `taskQueue`（按 `lastDrainedTasks`）（Stealing:L686-L691）
  ⇒ **中间任务与 tick 是两类不同粒度的实体**，同一 tick 的中间任务先于下一个 tick。
- 窃取时机：空闲自旋期（Stealing:L912-L917）+ 执行中间任务每轮开头（Stealing:L831-L835）；
  判据：候选必须比自己头部更早 + `now - holderStart >= stealThresholdNS`（Folia 取 **3 ms**，TickRegionScheduler.java:L96），
  再按 `behindBy / numaDistance` 打分；已 `stolen` 的不再窃取（防乒乓）（Stealing:L778-L816）。
- 窃取粒度 = **整个 tick 的归属权**（`ownedBy` 转移）；只有 `IDLE/HAS_TASKS` 可窃，`RUNNING*` 一律拒绝（Stealing:L457-L486）。
- 空闲线程**每 10 ms 自醒一次**以驱动窃取（`MAX_IDLE_TIME`，Stealing:L673/L912-L917）。
- 中间任务：`notifyTasks → scheduleTasks()`（IDLE→HAS_TASKS）；`executeTasksUntil(deadline)` 在 tick 的 deadline 前
  用空档 drain，`canContinue` 同时受"状态被中断"与**时间片 `taskTimeSliceNS`（Folia 取 2 ms）**约束（Stealing:L831-L883）。
- NUMA：`setThreadAllocation` 按节点分配线程并逐节点设亲和性；Folia 用 `FLAG_SCHEDULE_EVENLY`（TickRegionScheduler.java:L78），
  线程数 = `max(1, threads / nodes)`（TickRegionScheduler.java:L104-L115）。

### 3.4 保证与退化（对我们的意义）

- **公平性、优先级、硬延迟上界：都不提供。** Folia 用 `setScheduledStart(max(tickEnd, idealNextDeadline))`
  （TickRegionScheduler.java:L464）"拉平 deadline"换取"不饿死"，代价是**累积滑移**。
- 退化条件：单个 tick 长时间跑满会拖住同线程其它 tick（EDF 无迁移能力，最严重）；
  线程数 < 活跃区域数时多出的 tick 进 `queued` 队列等待。
- ⇒ 对我们是**好消息**：我们不需要发明"公平调度"；**只需要把 deadline 设定策略选对**
  （与上游一致：`max(tickEnd, idealNextDeadline)`），并且**不要**期待硬实时保证。

### 3.5 两个已知语义缺口（要记着，不要照抄）

1. EDF 的 `tryMarkCancelled()`/`CANCELLED` 是**死代码**（全项目无调用，EDF:L297-L299）。
2. `cancel()` 在 `queued.remove(state)` 成功那一支**不把 `scheduled` 置为 CANCELLED**（EDF:L248-L250），
   于是被取消的 tick 之后仍可能被 `returnTask` 重新排队（EDF:L399）。Folia 不依赖 `cancel`
   （它用 `AtomicBoolean cancelled` + 返回值自然摘除，TickRegionScheduler.java:L208-L212/L318-L320/L343-L346），
   所以我们若复用该库，**也不要依赖 cancel**。

## 4. 区块系统真正跑的池：`BalancedPrioritisedThreadPool`

（这一节是我补的；B 路子任务未覆盖。）

- 线程命名与数量（`paper-server/src/main/java/ca/spottedleaf/moonrise/common/util/MoonriseCommon.java`）：
  - `WORKER_POOL` → 线程名 `<Brand> Common Worker #N`（L18-L25）⇒ 实测 `Paper Common Worker #0..#3`
  - `IO_POOL` → `<Brand> I/O Worker #N`（L66-L73）⇒ 实测 1 个
  - 线程数：`defaultWorkerThreads = OSNuma...getTotalCores() / 2` → 再 `/= 2`（L43-L47），
    并可由系统属性 `<brand>.WorkerThreadCount` 覆盖（L49）；IO 线程 `max(1, configIoThreads)`（L57）
  - `CLIENT_GROUP` / `SERVER_GROUP`：`WORKER_POOL.createOrderedStreamGroup()`（L39-L40）
- **调度模型不是"每线程一队列 + 窃取"，而是"分组 + 时间片轮转"**：
  - `obtainGroup`：在所有有任务的组里选 `currentParallelism` 最小者，平手比"最久没被服务"（L259-L266、L298-L310）
    ⇒ 组间公平；`returnGroup` 递减并行度（L303-L305）
  - `WorkerThread.pollTasks`：取组 → `deadline = now + groupTimeSliceNS`（默认 **15 ms**，L21）→
    在该组内 `executeTask()` 直到没任务或时间片用完 → 归还组、换下一个组（L612-L641）
  - 组内任务由 `PrioritisedTaskQueue` 排序：`ConcurrentSkipListMap`，键序 = (优先级, subOrder, id)；
    开启 `FLAG_ORDER_BY_STREAM` 时 = (优先级, stream, subOrder, id)（PrioritisedTaskQueue.java:L46、L185-L215）
  - **异常不致命**：`pollTasks` 捕获 `Throwable` 只记日志（L634-L636）——与 Folia 区域 tick 的
    fail-stop 形成鲜明对比（见 §7 的取舍）
  - `adjustThreadCount(int)` 支持运行期调整线程数（L201）；`wakeupIdleThread()` 只唤醒**一个**空闲线程（L57-L63）

**对我们的直接含义**：我们的 hook（`onChunkHolderCreate/Delete`）就在这 4 个线程上执行，
并且**同一时刻最多 4 个 hook 并发**；区块系统自身用"优先级 + 时间片"而不是"线程独占"来保证吞吐，
所以我们**不能假设"同一区块的 hook 一定串行"**，只能假设"内核必须自己对并发安全"
（C1 的 `StampedLock` 已经满足这一点，但我们必须在 B 线把"归属"概念引入后才谈性能）。

### 5.3 我们的 hooks 所在的"现场合同"（★ 直接约束 C2 的实现，也约束 B3）

`onChunkHolderCreate`（`ChunkHolderManager.java:960` 调用）：
- 线程 = 触发票据传播的**任意**线程；**持有 `ticketLock`**（覆盖 section ±1 = 64×64 区块）；**不持** `schedulingLock`。

`onChunkHolderDelete`（`ChunkHolderManager.java:1187` 调用）：
- 线程 = **主线程**（L1193 断言）；持有 `ticketLock` + `schedulingLock`，但只锁该区块坐标。

**在 hook 里不能做的事**（这 5 条是我们必须在 B 线遵守的硬合同）：
1. **不能回调进区块系统** —— `scheduleChunkLoad/scheduleTickingState` 会检查锁并抛
   `IllegalStateException("Cannot schedule chunk load during ticket level update")`（`ChunkTaskScheduler.java:367-372/L571-576`）；
2. **不能触发新一轮票据更新** —— `BLOCK_TICKET_UPDATES` 期间 `processTicketUpdates()` 直接抛（`ChunkHolderManager.java:1478-1480`）；
3. **不能做 IO / 访问世界内容 / 加载区块** —— 你正持着 `ticketLock`，会阻塞同段所有区块的票据传播；
4. **不能抛异常** —— 会经 `ChunkProgressionTask.complete` → `unrecoverableChunkSystemFailure`
   变成**服务器 crash**（`ChunkTaskScheduler.java:293-325`）；
5. **不能反向取锁** —— 锁序已被固定为 `Moonrise ticketLock → Regionizer.lock`；
   `RegionizerCallbacks` 的契约（回调内不得阻塞/不得回调回区域化器/不得访问世界状态）必须保持。

⇒ C2 的实现（hook 里只做纯内存簿记 + 区域化器自己的 `StampedLock`）**符合合同** ✓；
B3/B4 若要"在 hook 里做更多事"（例如给段上票据），必须**改成投递到别处异步做**，不能在 hook 里同步做。

### 5.4 线程归属判定：**目前等于不存在**（★ 这是我们最该警惕的坑）

- `TickThread.isTickThreadFor(...)` 有 **11 个重载**，但在 Paper 版里**全部 `return isTickThread()`**——
  坐标语义被丢弃（`paper-server/src/main/java/ca/spottedleaf/moonrise/common/util/TickThread.java:129-171`）；
  `isTickThread()` = `instanceof TickThread`（`:121-123`）。
- ⇒ **只要我们的区域线程 `extends TickThread`，"违规访问"就会全部合法通过**。
  C3 施工图里那 52 个"线程归属校验"文件，在把 `isTickThreadFor` 改成 region-aware 之前，
  **保护力度为零**。
- 可检验判据（B2 的验收）：在非拥有区域的线程上调用
  `TickThread.ensureTickThread(world, chunkX, chunkZ, "...")` **必须抛 `IllegalStateException`**（当前不会）。

  当前实现指向一个 10 行的占位类（返回 `SECTION_SHIFT`）；
  **Folia 的真身返回 `config.gridExponent`**（`study/folia/src/.../TickRegions.java:28`）。
- ⇒ 接区域化时要做的第一步就是把这里接上（**让区块系统的锁粒度 ≥ 区域粒度**），
  这正是"区域化 = 把区块系统的独占单位从区块提升到区域"的机制化表达。

### 5.6 B3 段级票据的样板与坑

- 现成样板：`syncLoadNonFull`（`ChunkTaskScheduler.java:517-560`）演示了
  "加 `NON_FULL_CHUNK_LOAD` + BLOCKING 票据 → `managedBlock` 等待 → 撤票"。
- **但 `:514-516` 的注释明确写着**：Moonrise 可以阻塞是因为只有一个主线程；
  **在区域化下必须完全异步，否则区域间会死锁**。
- ⇒ B3 的验收用例必须包含"两个区域互相请求对方边界区块不得死锁"。

## 7. 对 CeruLean B 线的结论（B1–B6 怎么落地、难在哪）

### 7.0 三条总纲（研究结论的浓缩）

1. **"最难的那块"（调度器与并发原语）不需要我们写**：Folia 用的是
   `ca.spottedleaf.leafpile:concurrentutil:1.2.4`，而**我们的服务端已经依赖它**（Moonrise 在用，§6）。
   自研的部分应集中在**语义**（谁拥有哪块地、何时合并/分裂、跨区域怎么派发），不是**原语**。
2. **"区域化"在 Moonrise 侧已经有了接缝**：`ChunkTaskScheduler.lockShift = max(getRegionChunkShift(), SECTION_SHIFT)`
   加上注释"regioniser 假定同一 region section 内票据更新不并行"——把区域粒度喂进去即可（§5.5）。
3. **当前最大的风险不是性能，而是"保护为零"**：Paper 版的 `TickThread.isTickThreadFor` 全部
   `return isTickThread()`（§5.4）。区域线程一旦 `extends TickThread`，**所有归属违规都会静默通过**。
   B2 必须先把这一层做出来，否则后面的并发调试等于摸黑。

### 7.1 B1 调度骨架（难度：低-中）

- **直接用库**：`EDFSchedulerThreadPool`（546 行，与上游同类）作为 L1 起点；
  将来需要"中间任务填空档 + 落后 tick 迁移"时再换 `StealingScheduledThreadPool`（1156 行）。
- 需要我们自己写的只有"语义层"：
  - 实现 `SchedulableTick`：`runTick()` 里 tick 一个区域，`setScheduledStart(max(tickEnd, idealNextDeadline))`
    （与上游一致，TickRegionScheduler.java:L464）；
  - 区域 ↔ 调度句柄的映射（合并/分裂时如何迁移句柄，见 `TickRegions` 的 `copy()` 模式，
    TickRegions.java:L114-L117、L397-L405）；
  - 第一阶段**先用单线程确定性模式**（一个线程、固定顺序），用它和 C2 行为对拍。
- **判据**：单线程模式下 C2 验收与语义基线逐项一致（现成的对拍基线）。

### 7.2 B2 区域上下文 + 归属校验（难度：**高**，但必须最先做）

- 上下文：照上游用 `Thread` 子类 + 静态访问器（TickRegionScheduler.java:L260-L266），
  而不是 `ThreadLocal`（区域线程数量动态变化，且需要"取当前区域"的高频读）。
- **归属校验**：把 `TickThread` 的 **11 个 `isTickThreadFor` 重载**改成 region-aware
  （世界 + 坐标 → 区域拥有者线程），这才让施工图里 52 个文件的断言真正生效。
  这是 B 线**唯一必须"改上游文件"**的部分（`paper-server/src/main/java/.../TickThread.java`）。
- **判据（可检验）**：非拥有线程调用 `ensureTickThread(world, x, z, "...")` 必须抛
  `IllegalStateException`；且在压力用例下**不出现任何"合法通过"的违规**（把断言开在最严档）。
- 风险：断言过严会误杀（上游为此把很多检查放宽成"回退重排"而不是抛错，
  见 ChunkTaskScheduler.java:360/L564 的 `scheduleTickingState/scheduleChunkLoad` 模式）
  ⇒ 我们应**先抛错、逐条收敛**，而不是一开始就放宽。

### 7.3 B3 段级票据（难度：中-高）

- **挂点选择**：holder 钩子（C2 用的）暴露的是"holder 存在/消失"，**不是"内容存在"**
  （create 早于生成、delete 晚于内容消失，§5.3）。若票据要表达"这一段有内容要 tick"，
  应挂 `handleFullStatusChange` 的 content 分支（`NewChunkHolder.java:1250/L1287`，主线程、无需持锁）。
- **不能阻塞**：`syncLoadNonFull` 那种 `managedBlock` 模式在区域化下会死锁（§5.6）
  ⇒ 一律异步 + 回调。
- **判据**：两个区域互相请求对方边界区块时不得死锁；票据撤销后段能在下一次释放点被回收。

### 7.4 B4 跨区域派发（难度：中）

- 现成构件：`MultiThreadedQueue`（Folia 的任务队列用的就是它）+ `AreaDependentQueue`
  （按包围盒互斥，Moonrise 自己也在用）+ `ReentrantAreaLock`。
- 语义沿用我们已定的"**谁释放谁吸收**"与"跨区域延迟允许任意长"（docs/06 §8、lesson 09）。
- **判据**：跨区域用例行为符合预期；任意延迟下不丢任务、不死锁。

### 7.5 B5 内容并行（难度：**最高**，也是收益最大）

- 要做的其实是**把"必须主线程"的那几步改成"必须拥有该区域的线程"**：
  FULL 转换（`ChunkFullTask`）、FullChunkStatus 切换（`NewChunkHolder.handleFullStatusChange`）、
  卸载（`ChunkHolderManager.processUnloads`）、mid-tick 泵（`MinecraftServer.moonrise$executeMidTickTasks`）。
  这四处当前都以 `ensureTickThread`（= 必须是主线程）守卫（§5.2/§5.4）。
- `mainThreadExecutor`（`ChunkTaskScheduler.java:117`）必须变成**每区域一个**的任务队列，
  否则所有 world 内容都会挤回主线程。
- 区块生成那半边（Worker 线程 + `radiusAwareScheduler`）**本来就是并行的**，
  我们只要保证"区域粒度 ≥ 区块系统的锁粒度"（§5.5）即可，不必重写。
- **判据**：多区域并行 tick 时语义基线与 C2 一致；无数据竞争（B6 的压力用例）。

### 7.6 B6 压力与竞争检测（难度：中）

- 断言：B2 的 region-aware 归属校验 + 内核的 `verifyInvariants`（含 I2 快照）常开；
- 场景：多玩家各自游走（我们已有的 `MovementChurn` 场景）+ 跨区域交互 + 传送 + 关服；
- 判据：长时间运行无归属违规、无不变量违规、无死锁；关服能停住所有区域线程（`halt/join`）。

### 7.7 难度排序（诚实版）

| 排序 | 工作 | 为什么难 | 有现成答案吗 |
|---|---|---|---|
| 1 | B5 内容并行（把"主线程专属"改成"区域线程专属"） | 触碰服务端最核心的 tick 路径，隐藏耦合最多 | 上游有（52 文件施工图），但**量大** |
| 2 | B2 归属校验（11 个重载 + 52 处调用点） | 保护为零 ⇒ 必须自建；过严会误杀 | 上游有，需从补丁里取 |
| 3 | B3 段级票据（异步化） | 阻塞式样板不可照抄，死锁风险 | 部分（`syncLoadNonFull` 反向参考） |
| 4 | B6 竞争检测 | 需要长时间与多场景 | 我们已有内核不变量巡检 + 新场景 |
| 5 | B1 调度骨架 | 库已提供，主要是接线与语义 | **有，直接复用** |
| 6 | B4 跨区域派发 | 构件齐备，语义已定 | **有（`MultiThreadedQueue`/`AreaDependentQueue`）** |
