# 00 · Folia 是怎么接进 Paper 的（读源码前的总览）

> 这一课回答一个问题：**"区域化"这套东西，在工程上是怎样分片塞进 Paper/Minecraft 的？**
> 结论来自对两份补丁与本地 materialize 源码的交叉核对，每一处都标了出处。

## 1. 两份补丁的分工（数量说话）

| 补丁 | 目标源根 | 新增文件 | 修改既有文件 | 性质 |
|---|---|---|---|---|
| `minecraft-patches/0001-Region-Threading-Base` | `paper-server/src/minecraft/java/`（Minecraft 树） | **13** | 200（其中 187 个有实际 hunk） | 区域化**本体** + 对 Minecraft/Moonrise 的挂钩 |
| `paper-patches/0001-Region-Threading-Base` | `paper-server/src/main/java/`（Paper 自有树） | **0** | 206 | 对 Paper 自己那套代码的适配（配置/命令/事件/插件系统…） |

> 一个反直觉但重要的事实：**Folia 的 13 个新文件全在 Minecraft 树的补丁里**，包括包名是 `io.papermc.paper.threadedregions.*` 的那些。
> 原因是 paperweight 的补丁目录只是"应用目标"的区分，不按 Java 包名走。

## 2. 枢纽类：`TickRegions`（Paper 给它留了坑）

实测我们本地 materialize 出来的 **Paper 主线 26.3** 里：

```java
// cerulean-server/src/minecraft/java/io/papermc/paper/threadedregions/TickRegions.java
// placeholder class for Folia
public class TickRegions {
    public static int getRegionChunkShift() { return ThreadedTicketLevelPropagator.SECTION_SHIFT; }
}
```

Folia 的补丁把它从 **10 行扩成 486 行**（1 个 hunk，`@@ -1,10 +1,486 @@`），变成：

```java
public final class TickRegions
    implements ThreadedRegionizer.RegionCallbacks<TickRegions.TickRegionData, TickRegions.TickRegionSectionData> {
    private static int regionShift = 31;
    private static TickRegionScheduler scheduler;
    public static TickRegionScheduler getScheduler() { ... }
    public static void init(final GlobalConfiguration.ThreadedRegions config) { ... }
    private static int getTickThreads(final GlobalConfiguration.ThreadedRegions config) { ... }
    // + TickRegionData / TickRegionSectionData 两个数据类
}
```

**所以 `TickRegions` 是"区域化 ↔ Paper/Minecraft"唯一的对接面**：它既是 regioniser 的回调实现（回答"区域生死/分裂/合并"），又持有调度器单例、负责从配置算线程数。读懂它，等于拿到了整条接入链的地图。

`getRegionChunkShift()` 的语义也被改写了：主线返回 Moonrise 的 `SECTION_SHIFT`，Folia 改成自己的 `regionShift`（默认 31，由配置覆盖）——**"区域段"与"Moonrise 调度段"从同一概念变成两个概念**。

## 3. 启动链（谁在什么时候初始化区域化）

```
Paper 配置类 GlobalConfiguration           ← paper-patches 新增（206 个被改文件之一）
   └─ public ThreadedRegions threadedRegions;      // 配置段
        ├─ int  threads      = -1                  // ≤0 → 自动：cores/2，若 ≤4 则 1，否则再 /4
        ├─ int  gridExponent = 4                   // 区域网格 2^4 = 16 区块
        ├─ SchedulerType scheduler = EDF           // 调度策略
        └─ @PostProcess void postProcess() { TickRegions.init(this); }   // ← 配置解析完就初始化
                                                    │
                                            TickRegions.init(config)
                                                    │
                                    TickRegionScheduler(SchedulerType, threads)
                                                    │
              MinecraftServer 启动后期：RegionizedServer.getInstance().init()   // "only after loading worlds"
```

（出处：`GlobalConfiguration.java` 补丁 hunk；`08_0001-...patch` 第 5798 行附近 `init(config)`；第 8234 行 `RegionizedServer.getInstance().init()`）

**两个调度策略**（`TickRegionScheduler.SchedulerType`）：`EDF`（Earliest Deadline First，默认）与 `WORK_STEALING`（工作窃取）。
→ 这是**同一份区域化实现的两种调度行为**：做语义对比时，策略不同会导致 tick 顺序不同，必须显式声明用的是哪种。

## 4. 类归属速查（移植时最容易放错的地方）

| 位置 | 内容 |
|---|---|
| `src/minecraft/java/…`（Minecraft 树） | `TickRegions`（占位被填充）、13 个 Folia 新文件、以及对 `net/minecraft/**`、`ca/spottedleaf/moonrise/**` 的 187 处改动 |
| `src/main/java/…`（Paper 自有树） | 主线已有的 `EntityScheduler`、`scheduler/{FallbackRegionScheduler,FoliaAsyncScheduler,FoliaEntityScheduler,FoliaGlobalRegionScheduler}`；Folia 对其中 206 个文件的适配改动（含 `GlobalConfiguration`、Bukkit/CraftBukkit 实现等） |

**同包不同源根**（`io.papermc.paper.threadedregions` 横跨两棵树）在编译期合并——CeruLean 移植时必须逐个类确认归属。

## 5. 对 CeruLean 的直接启示

1. **接入面很窄**：对外只有 `TickRegions`（回调实现 + 调度器单例 + 配置入口）与 `RegionizedServer`（全局 tick 生命周期）两个"公共接口"，其余都是内部实现。这降低了移植的接口风险。
2. **配置即语义**：`gridExponent=16 区块`、`threads`、`scheduler=EDF` 三个值直接决定行为。CeruLean 必须**显式记录自己的取值并写进基线文档**，否则"语义一致"无从判定。
3. **主线已经预留了坑位**（`// placeholder class for Folia`）——说明 Paper 官方对这条分支是"知情且留门"的。这既是好消息（未来可能继续靠近），也是风险（上游可能按自己的设计填充这些坑位，与我们的实现冲突）。
4. **要警惕的移植陷阱**：`TickRegions` 是**静态单例 + 静态可变状态**（`regionShift`/`initialised`/`started`/`scheduler`）。多 world、重启、测试隔离都会受影响；我们的实现若沿用这个形态，必须确保测试之间能重置。
