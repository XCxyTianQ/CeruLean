# 02 · 分裂与合并：区域边界究竟在什么时候变

> 源码：`ThreadedRegionizer.java` 精读范围 `276–673`（`addChunk`/`removeChunk`/`onRegionRelease`）+ `805–994`（`ThreadedRegion` 生命周期）。
> **本课回答了第 01 课留下的关键问题**：一条跨区域的命令方块链，它的区域边界是谁、在什么时刻决定的。

## 1. 状态机与两个"握手"集合

```java
private static final int STATE_TRANSIENT = 0;   // 过渡态：有挂起的合并，不可 tick
private static final int STATE_READY     = 1;   // 就绪：无挂起合并，可被标记 tick
private static final int STATE_TICKING   = 2;   // 正在 tick（被 tick 线程持有）
private static final int STATE_DEAD      = 3;   // 已死
```

合并意图用**两个集合成对表达**（L873 附近定义）：

| 集合 | 含义 |
|---|---|
| `mergeIntoLater` | 我**要**合并进的那些区域（我 → 它们） |
| `expectingMergeFrom` | 那些区域**要**合并进我（它们 → 我） |

两者必须严格互为镜像 —— `mergeIntoLater()` 里同时 add 两边并**校验两个 add 的返回值一致**，不一致直接抛异常（L895–903）。这是防"合并意图泄漏"的自检。

## 2. `addChunk`：合并主要发生在这里（L276–449）

```
addChunk(chunkX, chunkZ)
├─ 快路径（不加锁）：段已存在且非空 → section.addChunk() 返回
│    前提假设（代码注释明确写出）：同一段内不会并行 add/remove
└─ 慢路径（写锁）：
     ├─ 段不存在则新建段；否则加区块
     ├─ 在 createRadius + mergeRadius 的方形范围内扫描邻居：
     │    · 遇到已有段 → 收集进 nearbyRegions
     │    · createRadius 内的空邻居 → 建"空段"并 incrementNonEmptyNeighbours()
     ├─ nearbyRegions == null（孤立）
     │    → new ThreadedRegion + addSection… → onCreate()（含 onRegionCreate 回调）
     └─ 有邻居：
          ├─ 挑一个**不在 TICKING** 的邻居当 regionOfInterest；没有就新建
          ├─ 把新段加进 regionOfInterest
          ├─ 其余邻居逐个处理：
          │    killAndMergeInto() 成功 → 立即合并（真合并，含数据迁移）
          │    失败（对方正在 TICKING）→ 记为 mergeIntoLater（挂起合并）
          ├─ 若 regionOfInterest 是复用的旧区域、且因此产生了挂起合并
          │    → state = TRANSIENT + callbacks.onRegionInactive()
          └─ 只有当"新建且无任何挂起合并"时 → state = READY + onRegionActive()
```

**关键点**：`STATE_TICKING` 的区域**不能被合并**（`killAndMergeInto` 见 L833–835 直接 `return false`）。所以"正在 tick 的区域"享有天然的稳定性。

## 3. `removeChunk`：**不触发分裂**（L451–496）

它只做两件事：

1. 快路径：段内区块数 > 1 → 直接移除（无锁）；
2. 慢路径（写锁）：移除区块 + 遍历 `emptySectionCreateRadius` 范围内的邻居，逐个 `decrementNonEmptyNeighbours()`。

**没有任何分裂逻辑**。这一点非常反直觉，也是本课最重要的发现之一：

> **区域拓扑的重算被推迟到"区域停止 tick 的那一刻"**，而不是每次区块增删时。

## 4. 真正发生分裂/合并的地方：`onRegionRelease`（L499–672）

调用链只有一条：`ThreadedRegion.markNotTicking()`（写锁内，要求 `state == TICKING`）→ `regioniser.onRegionRelease(this)`。

`onRegionRelease` 分五个阶段：

| 阶段 | 动作 |
|---|---|
| ① 执行挂起合并 | 若 `expectingMergeFrom` 非空 → 逐个 `killAndMergeInto(本区域)`（含 `preMerge` 回调 → `tryKill()` → `mergeInto()` 数据迁移）；合并完若自己**仍**有 `mergeIntoLater` → 转 `TRANSIENT` + `onRegionInactive` 并 **提前 return**（把后续清理交给"我将要合并进去"的那个区域） |
| ② 判断是否回收死段 | `removeDeadSections = hasExpectingMerges \|\| hasNoAliveSections() \|\| (sectionCount >= minSectionRecalcCount && deadSectionPercent >= maxDeadRegionPercent)` ← **五个设计旋钮里的两个用在这里** |
| ③ 校验并移除死段 | 每个死段必须"空且无空邻居"（否则抛异常），再从 `region.sectionByKey` 与全局 `sections` 表移除 |
| ④ 提前返回条件 | **没回收任何死段 → 直接 `state = READY` 返回，不检查分裂** |
| ⑤ 分裂（仅当回收了死段） | BFS 求连通分量（半径 = `max(regionSectionMergeRadius, emptySectionCreateRadius)`）→ 只有 1 块则不分裂；多块则：`preSplit(old, 新区域列表)` → 旧区域 `DEAD` + `onRemove(true)`（= `onRegionInactive` + `onRegionDestroy`）→ 逐段 `setRegionRelease(null)` 并归入新区域（校验无重复归属）→ `data.split(regioniser, into, regions)` → **最后**才给新区域 `READY` + `onCreate()` + `onRegionActive()` |

### 三个顺序设计要点（值得学）

1. **先声明后执行**：`preSplit` 在旧区域死亡**之前**调用、并把新区域对象一起交出来；`preMerge` 在 `tryKill` **之前**调用。
2. **数据层最后动**：拓扑先改完，`data.split/mergeInto` 再迁移数据；且它们**全程在写锁内**（所以回调契约禁止碰世界状态——见 01 课）。
3. **分裂是"回收死段"的副产物**：`minSectionRecalcCount` 与 `maxDeadRegionPercent` **不是纯性能旋钮，而是分裂发生的必要条件**。把这两个值调大/调小，会直接改变"一个世界会被切成几个区域"。

## 5. 对第 01 课关键问题的回答

> **问**：一条跨区域的命令方块链，它的区域边界是谁、在什么时刻划出来的？

**答**（有代码依据）：

- 边界**不是谁主动"画"的**，而是 `addChunk`（邻居扫描 + 合并）与 `onRegionRelease`（回收死段后 BFS 分裂）这两套规则**自然涌现**的；
- 边界**只在区域停止 tick 的那一瞬间**（`markNotTicking` → `onRegionRelease`）才可能变化；
- 而且当区域处于 `STATE_TICKING` 时：既不能被合并（`killAndMergeInto` 对 TICKING 返回 false），新的合并请求只会被挂起，同时 `tryMarkTicking` 要求 `READY` 且无挂起合并 —— 于是得到一条重要保证：

> **一个正在 tick 的区域，其区块集合在整个 tick 期间是稳定的。**

由此可以推出（这就是 AzureBranches 那 9 个类存在的理由）：

- 若一条命令方块链**完全落在单个区域内** → 它在一次 tick 内有确定的、串行的执行顺序；
- 若链**跨越两个区域** → 两个区域**各自独立 tick**，链的推进就没有单一时间线，中间状态可能被另一个区域的 tick 观察到 → **语义断裂**；
- Folia 本身**不解决**这个问题（它只保证"区域内部串行"），所以必须在区域化之上再叠一层协议（AzureBranches 的 OCC：阶段快照 + 读集/写集校验 + 补偿）。

**换句话说：Folia 提供的是"分隔"，AzureBranches 补的是"跨越分隔的一致性"。** 这条界线现在从源码上被确认了。

## 6. 无锁快路径与其前提（并发设计的示范）

| 位置 | 快路径条件 | 代码里写明的前提 |
|---|---|---|
| `addChunk` | 段存在且非空 | "for each section, no addChunk/removeChunk can occur in parallel"（L281–282） |
| `removeChunk` | 段内区块数 > 1 | 同上（L456–457） |

把并发前提**写在注释里并与快路径紧邻**，是这套代码值得借鉴的地方：读者不需要去别处找假设。

## 7. 移植启示与待确认项

**启示**
1. **移植区域化 ≠ 移植几个类**：真正的工作量在"把 addChunk/removeChunk 挂到正确的地方"——第 10 课要确认 `ServerLevel`/`ChunkMap` 是在哪些事件里调用它们的。
2. **分裂只在释放时发生**，这意味着区域化下的世界状态迁移有一个**天然的静默点**；如果我们自己实现，必须保留这个性质，否则数据迁移会与 tick 并发。
3. **`STATE_TICKING` 的"不可合并"保证**是区域化语义的基石之一；任何"为了性能放宽它"的改动都会破坏可推理性。

**待确认（留给后续课）**
- `ThreadedRegionSection` 的 `nonEmptyNeighbours` / `deadSections` 如何随区块增删演化（第 04 课）；
- `RegionizedData`/`RegionizedWorldData` 在 `data.split/mergeInto` 里到底迁移了什么（第 05/06 课）——**这是"跨区域时实体/方块实体怎么办"的答案所在**；
- `ServerLevel` 是在哪些事件里调用 `addChunk`/`removeChunk`、以及传给 regioniser 的**五个旋钮的实际取值**（第 10 课；对应 `GlobalConfiguration.threadedRegions.gridExponent = 4` → 段 = 16 区块）。
