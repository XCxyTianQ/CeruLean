# 02 · 复现校验手册

## 为什么需要它

Paperclip 风格的发行物是"**启动器 + 二进制补丁 + 依赖库**"，服务端本体在首次启动时才由「Mojang 原版 server.jar + 补丁」合成。这意味着：

- 用 `unzip` 看到一个 30 MB 的 jar，**里面没有一行 Minecraft 业务代码**；
- 想审计/二次开发/验证来源，必须先**自己复现**合成过程；
- 一旦能复现，就能把"我们的发行物是否只在预期处偏离上游"变成**可判定的哈希断言**。

## 工具

`tools/verify/cerulean-verify`（JDK 17+ 单文件源码运行，零第三方依赖；下载走 `curl`）

| 子命令 | 作用 |
|---|---|
| `upstream --version <v> [--build N\|--channel STABLE] [--jar f] [--no-apply] [--report f.json]` | 复现上游发行 jar，逐环校验哈希 |
| `inspect <jar>` | 打印五个清单（main-class / download-context / versions / patches / libraries）+ MANIFEST |
| `diff <jarA> <jarB> [--top N] [--json f]` | 类级 CRC-32 漂移报告（新增/删除/改动 + 体积变化排行） |
| `selftest [--version v] [--build N]` | 负向自测：篡改补丁/依赖库必须被检出 |

## 校验链（`upstream` 逐环）

```
容器 sha256（对比 Fill API 发布值）
  → 五个清单存在且可解析
    → 内嵌补丁 sha256 == patches.list 的 patchHash
      → 内嵌依赖库 sha256 == libraries.list 各行哈希（未内嵌的 39 个由原版 bundler 提供）
        → 原版 bundler sha256 == download-context 的哈希
          → 内层 server jar sha256 == patches.list 的 originalHash
            → 应用 bsdiff 后 sha256 == outputHash   ★ 决定性一步
```

任何一环失败即退出码 1，并列出失败项。

## 实测基线（2026-10-12）

Paper 26.3 build 175（STABLE）全链通过：

| 环节 | 值 |
|---|---|
| 容器 | `ece5afb6…` · 55,142,601 B |
| 原版 bundler | `d052f14d…` · 62,294,556 B |
| 内层 server jar | `a362163e…` · 26,652,008 B |
| 补丁 | `3e5c31dc…` · 22,081,250 B |
| **输出（成品）** | **`7afb0563…` · 30,909,724 B** |

`selftest` 基线：未篡改 PASS；篡改补丁 FAIL（patchHash 不符）；篡改依赖库 FAIL（库哈希不符）。

## 供应链加固（Phase 1 待办）

当前实现**从被校验的容器内提取补丁器类**（jbsdiff，与 Paperclip 官方运行时行为一致），信任链是"先验证容器哈希，再使用其内置补丁器"。

加固方案（Phase 1 落地）：把 jbsdiff 与 commons-compress 的类**vendoring 进 `tools/verify/vendor/`**，并在 `vendor/MANIFEST.sha256` 记录来源与哈希，使校验过程**完全不依赖被测对象**。决策点：vendoring 需引入 Apache-2.0 依赖的许可声明，与 GPLv3 主许可并存（兼容，但需在 NOTICE 中列明）。
