## 7. ★ 根因定论（2026-10-16 实测，一次连接一条命令的对照实验）

**不是** RCON 响应交错，**也不是**我们补丁无效，而是：

> **Folia 自己把 `data` / `scoreboard` / `clone` 的注册注释掉了**，`fill` 与 `setblock` 保留。

Folia 26.3 补丁原文（`folia-server/minecraft-patches/features/0001-Region-Threading-Base.patch`）：

```diff
-        DataCommands.register(this.dispatcher, context);
+        //DataCommands.register(this.dispatcher, context); // Folia - region threading - TO…
-        ScoreboardCommand.register(this.dispatcher, context);
+        //ScoreboardCommand.register(this.dispatcher, context); // Folia - region threading
         FillCommand.register(this.dispatcher, context);        ← 保留
         SetBlockCommand.register(this.dispatcher, context);    ← 保留
```

**与探针逐条吻合**（每条命令独立连接、结构上排除响应交错）：

| 命令 | 实测响应 | 解释 |
|---|---|---|
| `fill` | `That position is not loaded` | 正常业务响应 ⇒ 已注册 ✓ |
| `setblock` | （无输出/成功） | 已注册 ✓ |
| `data get block` | `Unknown or incomplete command` | **未注册** ✗ |
| `scoreboard …` | 同上 | **未注册** ✗ |
| `clone` | 同上 | **未注册** ✗ |

⇒ 我们此前把"命令失败"归因于"缺跨区域投递"**不完全准确**：真正的一级原因是**上游为区域安全化而暂时下架了它们**（注释里的 TODO）。
这也正是 AzureBranches 的 EXP 工作在做的事——**把下架的命令重新启用并做成区域安全**。

## 8. 由此确定的移植动作（清单更新）

1. **重新启用注册**：在我们自己的补丁里把这三条命令的注册放开（uncomment），一行一处 ✓；
2. **同时补区域安全**（否则放开即崩/行为错）：
   - `data`：已完成 `AwaitableDispatch` + `BlockDataAccessor` 投递（本分支 `0012-CeruLean-data-owning-region.patch` ✓ 编译通过）；
   - `scoreboard`：先甄别触碰区域内容的子命令（多数是全局状态 ✗ 不应异步化）；
   - `clone`：照 `setblock` 模板投递到**目标区域**；
3. 重新构建后用本文件的探针复测（预期：三条命令从"未知命令"变为正常业务响应）✓；
4. 之后才轮到 `0012` EXP 链本体与 `0013` 差额比对。

## 9. ★ 对齐实验成功：`data` 命令已在 Folia 26.3 基座上安全复活（2026-10-16 实测）

### 9.1 三步走的完整闭环

| 步 | 现象 | 处理 |
|---|---|---|
| 1 | `data get block …` → `Unknown or incomplete command` | 查明是 **Folia 主动注释掉注册**（下架）⇒ 我们补丁放开注册（`0013`） |
| 2 | 报错变为 `An unexpected error occurred…`（**已注册** ✓） | 从控制台栈定位到 `BlockDataAccessor.lambda$static$2:30`——**参数解析期**在调用者线程上读方块实体 ✗ |
| 3 | — | 把世界访问**整体推迟**进投递体：`PROVIDER` 只解析位置，`BlockDataAccessor` 改持 `(level,pos)`，实体读取与读写都在 `AwaitableDispatch` 的投递体内执行（`0012` 重写） |

### 9.2 验证结果（每条命令独立连接，结构上排除响应交错）

```
$ setblock 100 100 0 minecraft:command_block{Command:"say hello"}   → （成功）
$ data get block 100 100 0 Command
      → 100, 100, 0 has the following block data: "say hello"        ✅ 正确返回
$ fill 200 100 0 201 100 0 minecraft:stone
      → That position is not loaded                                   ✅ 正常业务响应
$ scoreboard … / clone …
      → Unknown or incomplete command                                 ⏸ 按计划仍禁用（未做安全化）
```

`applyAllPatches` 0、`createPaperclipJar` 0 ✓。

### 9.3 结论

- **上游 `setblock` 模板确实覆盖 `data`** ✓ —— 对齐实验的假设被证实（这是本轮最关键的结论）；
- 但**只用模板不够**：真正的难点是**"参数解析期也不能访问世界"**（第 2 步），
  这正是 Folia 当初下架这些命令的原因，也是 AzureBranches 必须**整文件重写** `SetBlockCommand`
  这类文件、而不能只加一行投递的原因 ✓（与 docs/13 §3 的判断一致）；
- 下一步照同样三步处理 `scoreboard`（先甄别触碰区域内容的子命令）与 `clone`（投递到目标区域）。

### 9.4 一处待改进（诚实记录）

`AwaitableDispatch.call` 采用"投递 + 闩锁等待（5 s 超时）"，**若调用方本身是别的区域的 tick 线程会短暂阻塞该区域** ✗。
对齐阶段接受；生产实现应换成 AzureBranches 的 continuation（不阻塞，已在库内 `com.azurebranches.command.Continuation` ✓）。
