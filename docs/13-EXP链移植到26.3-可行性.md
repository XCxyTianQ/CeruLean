# 13 · EXP 链移植到 Folia 26.3 基座：可行性评估（含实测）

> 前置：`docs/EXP链移植可行性分析.md`（早期会话，**基于 Paper 主线**）给出了"耦合仅 ≈8 个调用点、
> `azurebranches-common` 3357 行纯 JDK、语义复现 ≈85%"等结论。
> 本文件补上**基座已换成 Folia 26.3**之后的重新评估——前提变了，结论也要跟着变。

## 1. 前提变化（这是本次评估最重要的部分）

| 旧分析里判定"缺失、需自建"的东西 | 现在（Folia 26.3 基座） | 证据 |
|---|---|---|
| `RegionizedServer` | ✅ **存在** | `io/papermc/paper/threadedregions/RegionizedServer.java:50`（`getInstance()`） |
| `RegionizedTaskQueue.queueOrExecuteTickTask(...)` | ✅ **存在** | `RegionizedTaskQueue.java:75` |
| `ThreadedRegionizer` | ✅ **存在** | `ThreadedRegionizer.java:29` |
| `TickRegions.getRegionChunkShift()` | ✅ **存在** | `TickRegions.java:32` |

**旧分析的三个阻塞项全部消失** ⇒ 移植不再需要"先自建区域化器"，那 8 个调用点**可以直接照写** ✓。

## 2. ★ 上游已经吸收了一部分（实测）

Folia 26.3 的 `0001-Region-Threading-Base` 给 `SetBlockCommand` 加了：

```java
RegionizedServer.getInstance().taskQueue.queueOrExecuteTickTask(
        level, pos.getX() >> 4, pos.getZ() >> 4, () -> { ... });
```

也就是说 **"setblock 跨区域投递到拥有者并等待"已经是上游行为** ✓
⇒ AzureBranches 的 `0013-AzureBranches-exp-awaitable-setblock.patch`（26.1.2 时代）
**其分发部分已被上游吸收**，只剩"awaitable 语义是否超出上游"这一小块需要比对。

这也解释了我们的冒烟失败清单：失败的是 **`data get` / `fill` / `clone` / `scoreboard` / `execute if`**
——**恰恰是还没有 `queueOrExecuteTickTask` 待遇的那些命令** ✗，
而 `setblock` 不在失败清单里 ✓（它已经有上游的区域投递）。

## 3. 逐块可行性

| 块 | 规模 | 冲突面 | 可行性 | 说明 |
|---|---|---|---|---|
| `0012-exp-chain`（`CommandBlock.java`） | EXP 改写版 **500 行** vs 26.3 版 **216 行** ⇒ 差异 **292 行** | 该文件 Folia 侧改动很少（26.3 版内无 Folia/Regionized 痕迹） | **中-高** | 主要工作＝把 EXP 的链状态机（可挂起/可恢复/阶段快照/延迟动作）重新落到 26.3 的 `CommandBlock` 上；上游漂移小是有利条件 |
| `0013-awaitable-setblock` | EXP 244 行 vs 26.3 163 行 ⇒ 差异 137 行；**26.3 版已含 8 处 Folia 相关改动** | **与上游重叠** | **高（可能大部分不需要）** | 先逐行比对"上游已做的投递"与"EXP 的可等待语义"，只补差额 |
| `0011-command-block-mode` + `0009-config-init` | 小 | 配置系统不同 | **高** | 接到我们的配置节即可（模式开关 + 兼容性降级） |
| `azurebranches-common`（9 类 / 3357 行） | 纯 JDK，**零 MC import** | 无 | **很高** | 可整包搬入（`cerulean-regions` 或新模块），只需接配置与命令注册 |
| 另外 4 个命令（`fill`/`clone`/`data`/`scoreboard`） | 新增工作 | 无上游先例 | **中** | 这 4 条是我们冒烟实测出来的**真实缺口**；照 `setblock` 的上游写法补 `queueOrExecuteTickTask` 语义即可（模式已验证可行 ✓） |
| OCC 协议状态用 `ThreadLocal`（旧分析风险 1） | — | — | **风险仍在** | 与版本无关的设计问题：需改成区域作用域（否则区域分裂/合并下语义错） |

## 4. 结论与概率（更新）

| 目标 | 旧评估（Paper 主线） | **本次评估（Folia 26.3 基座）** | 变化依据 |
|---|---|---|---|
| 语义复现（单线程/单区域跑通，行为等价） | ≈85% | **≈95%** | 阻塞项（需自建的区域化器/任务队列）已消失，且 `setblock` 的上游先例证明了模式可行 |
| 完整跨区域语义（分裂/合并下仍正确） | ≈60–70% | **≈80%** | 同上；剩余不确定性集中在 OCC 状态作用域与命令方块的链快照语义 |
| 代码可直接复用比例 | 纯 Java ~70% | **纯 Java ~90% 可照搬**（`azurebranches-common` 零依赖）；两个整文件改写需重落 | 基座就位 |

**工作量估算（人日，含验收）**：`0012` 移植 1–2；`0013` 比对+补差 0.5–1；
`0011`/配置 0.5；common 模块搬入+接线 0.5；四条命令补 `queueOrExecuteTickTask` 语义 1–1.5；
验收（复用他们的 `exp6/exp6plus/exp7-smoke.py` + 我们的 L2 层）1 ⇒ **合计 ≈4.5–6.5 人日**。

## 5. 建议路径

1. **先做 30 分钟的对齐实验**：把 `setblock` 的上游写法作为模板，给 `fill` 补上
   `queueOrExecuteTickTask`，用我们的 L2 探针验证"命令不再报 Unknown or incomplete command" ✓
   ——这能**在最小成本下证伪/证实"上游模式可覆盖这 4 条命令"**；
2. 再搬 `azurebranches-common`（零风险）+ `0011` 模式开关；
3. 然后攻 `0012`（EXP 链本体，最大块）；
4. 最后处理 OCC 状态作用域（设计改动，单独评估）；
5. 全程用他们的 `exp*_smoke.py` 当验收参照，并纳入我们的套件（L2 层）。

## 6. 一句话

**旧分析说"能复现、但要先把区域化器自建出来"；现在基座换成了 Folia 26.3，
那道墙没了**——而且上游已经把 `setblock` 的跨区域投递做掉、正好给出可照抄的模板，
剩下真正的工作是 **EXP 链本体（292 行改写）+ 四条命令的补齐 + OCC 状态作用域**。
