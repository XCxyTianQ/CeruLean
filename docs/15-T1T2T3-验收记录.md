## 3. ★ 本轮的第二个根因：不是"区块所有权"，是"区域 tick 上下文"

`docs/13` §7 定的根因（Folia 注释掉注册）只是**一级原因**。放开注册后仍然崩，栈顶给出二级原因：

```
[ERROR]: Command exception: /clone 96 100 0 96 100 0 100 100 0
java.lang.NullPointerException: Cannot read field "captureTreeGeneration"
    because the return value of "net.minecraft.world.level.Level.getCurrentWorldData()" is null
	at net.minecraft.world.level.Level.getBlockState(Level.java:1349)
	at net.minecraft.world.level.block.state.pattern.BlockInWorld.getState(BlockInWorld.java:26)
	at net.minecraft.server.commands.CloneCommands.clone(CloneCommands.java:218)
	...
	at net.minecraft.server.dedicated.DedicatedServer.lambda$runCommand$0(DedicatedServer.java:903)
	at io.papermc.paper.threadedregions.RegionizedServer$GlobalTickTickHandle.runOneTask(RegionizedServer.java:199)
```

由最后一帧可知：**RCON 命令跑在 global region tick 线程上**（`DedicatedServer.runCommand`
把命令体 `runAsync(..., RegionizedServer.getInstance()::addTask)`）。

而 `Level.getCurrentWorldData()` 的实现是：

```java
public RegionizedWorldData getCurrentWorldData() {
    final RegionizedWorldData ret = TickRegionScheduler.getCurrentRegionizedWorldData();
    if (ret == null) return ret;                       // ← 没有区域 tick 上下文 ⇒ null
    if (ret.world != this) throw new IllegalStateException("World mismatch: expected …");
    return ret;
}
```

⇒ **规则比"拥有该区块"更严**：

| 调用者线程 | `level.getBlockState(...)` |
|---|---|
| 正在 tick 该 level 的区域线程（且该区域含此区块） | ✅ 正常 |
| 没有区域 tick 上下文的线程（global region tick、控制台、插件主线程） | ✗ **NPE**（`getCurrentWorldData()` 为 null） |
| 别的 world 的区域线程 | ✗ `IllegalStateException: World mismatch` |
| 该 level 的区域线程但不拥有该区块 | ⚠️ 不报错（`ServerChunkCache.getChunk` 只读 `fullChunks`，无所有权断言）——与上游 `FillCommand` 的取舍一致 |

所以"把世界访问挪进**该 level 的**区域线程"是唯一正确做法，而"投递到目标区域的拥有者"同时满足这两条。

## 4. T1 scoreboard：结论是"只需放开注册 + 无需投递"

### 4.1 实测

`0014` 放开 `ScoreboardCommand.register` 后，**全部 21 个用例直接正常响应**，没有任何运行时异常：

```
$ scoreboard objectives add ceruprobe dummy        → Created new objective [ceruprobe]
$ scoreboard objectives modify ceruprobe rendertype hextime    → （成功）
$ scoreboard players set holder ceruprobe 7        → Set [CeruProbe] for holder to 7
$ scoreboard players operation holder ceruprobe += holder ceruprobe → Set … to 12
$ scoreboard players display name holder ceruprobe {"text":"H"} → Changed display name to H …
$ scoreboard objectives setdisplay sidebar ceruprobe → Set display slot sidebar to show objective CeruProbe
$ scoreboard players set @e[limit=1] ceruprobe 3   → No entity was found   ← 正常业务响应（选择器已解析）
$ scoreboard objectives remove ceruprobe           → Removed objective [CeruProbe]
```

### 4.2 为什么不需要投递

逐条查过计分板命令里**唯一可能碰世界的入口**是 `ScoreHolderArgument` 的实体选择器
（`@e`/`@a`），实测它返回的是"正常业务响应"（`No entity was found`）而不是 NPE
⇒ 该解析**不经过** `Level.getBlockState` 那条 `getCurrentWorldData()` 路径。

其余路径只做两件事：
1. 读写 `Scoreboard` 容器（server 级共享对象，不经 level）；
2. `ServerScoreboard.broadcastAll/startTrackingObjective/stopTrackingObjective` 遍历在线玩家发**网络包**
   ——`connection.send` 本来就是 Folia 允许跨线程调用的。

⇒ T1 的验收（"正常返回、不引入区域线程阻塞"）**达成**：这些操作全在调用线程内联完成，
`/cerulean dispatch` 自检显示 `callBlocking` 不因计分板命令增长。

### 4.3 ⚠️ 一并记录的残余风险（没有解决，别当已解决）

`Scoreboard` 是**跨区域共享、且没有任何同步**的容器，而它**在放开命令之前就已经被区域线程写**：

| 写入点（全部在实体 tick / 区域线程上） | 路径 |
|---|---|
| `ServerPlayer.awardStat(…):2610` / `resetStat(…):2616` | → `forAllObjectives` → `Scoreboard.getOrCreatePlayerScore` |
| `ServerPlayer.awardKillScore(…):1446` / `handleTeamKill(…):1466` | 同上 |
| `ServerPlayer.updateScoreForCriteria(…):1260` | 同上 |

`Scoreboard.playerScores` 是 `Object2ObjectOpenHashMap`。放开 scoreboard 命令等于**在 global tick 线程上
再加一个写者**，与上述区域线程写者并发（`computeIfAbsent` 与并发读写在极端时序下可致结构损坏）。

- 这是 Folia 把该命令下架的**合理嫌疑之一**，但**本会话没有给出修复**：正确做法是给 `Scoreboard`
  的读写加区域安全的同步（或改成单线程 owner），属于**设计改动**，量级等同 OCC 那一类。
- 因此 T1 的状态是"**功能已复活的验收标准达成**"，不是"区域安全已证明"。
  若要与上游保守策略对齐，可在 `AzureBranchesConfig` 里给 scoreboard 加开关（默认关）。

## 5. ★ T3：对 `docs/14` 方案的一处事实更正

`docs/14` §6/T3 写的是"把 `AwaitableDispatch` 换成不阻塞实现，用 `com.azurebranches.command.Continuation`"。
**这条不能照做**，两个独立原因：

1. **`Continuation` 不是通用投递原语**。它是 EXP 命令方块链**挂起态的快照**（`traversalId`/`cursorPos`/
   `direction3d`/`remaining`/各 carry 映射），生命周期由 `ChainHead` 的状态机驱动，
   只在"链遍历被跨区域操作挂起、之后由 home region 线程恢复"这一场景里有意义。
   它没有"投递任意 supplier 并取回结果"的能力。（读 `Continuation.java` 头部注释即可确认。）
2. **`data get` 的等待在命令契约上无法消除**。证据链：
   - Brigadier 命令返回 `int`，返回值必须在命令体返回前算出；
   - `DedicatedServer.runCommand` 在**读取 RCON 响应之前**只 `join()` 了 global region 那一个任务：
     ```java
     CompletableFuture.runAsync(sync, RegionizedServer.getInstance()::addTask).whenComplete(…).join();
     return rconConsoleSource.getCommandResponse();     // ← 响应此刻就被取走了
     ```
   - 若把 `data get` 改成 fire-and-forget，响应会变成**空串**（对照：`setblock`/`clone` 修好后就是空响应）。

### 5.1 实际交付的 T3

`AwaitableDispatch` 拆成两个语义明确的原语（`cerulean-regions/.../io/cerulean/regions/AwaitableDispatch.java`）：

| 原语 | 阻塞 | 用于 |
|---|---|---|
| `dispatch(level, pos, Runnable)` | **不阻塞**：拥有者内联，否则 `queueOrExecuteTickTask` 后立即返回 | 一切**写路径**与不需要返回值的命令体（`clone`、`data set`、setblock 类） |
| `call(level, pos, Supplier<T>)` | 拥有者内联；否则投递 + 有界等待（5 s 超时） | 只有"命令契约要求同步返回值"的读取：目前仅 `data get` |
| `owns(level, pos)` | — | 给"内联取结果 / 投递占位返回"的分支用 |

**自检**（T3 验收要求的"可加自检"）：`call()` 记账并在首次阻塞时 WARN 一次（含线程名/位置/是否 tick 线程），
并新增命令 **`/cerulean dispatch`** 输出快照：

```
inline=… queued=… callBlocking=… callBlockingTotalMs=… callBlockingFromTickThread=… lastBlockingSite=…
```

实测（探针内联断言）：

```
callBlocking（clone 之前）= 3
  跑 clone / setblock（写路径，走 dispatch）后
callBlocking（写路径之后）= 3     ← 写路径零阻塞 ✓
  data get（读路径，走 call）
callBlocking（data get 之后）= 4  ← 只有"必须同步取值"的读会等待 ✓
```

⇒ T3 验收中"**从区域线程发起跨区域调用不再阻塞**"对**写路径**成立并已断言；
读路径那一次等待是**命令契约的固有代价**（已给出代码路径证据），
真要消除需改 `DedicatedServer.runCommand` 让"命令未完成"对 RCON 可见——另一个量级的改动，不在本案范围。

## 6. T2 clone：修法

`cerulean-server/minecraft-patches/features/0015-CeruLean-clone-owning-region.patch`：

1. 参数解析期与**纯数学/纯 chunk-source 检查**（重叠检测、`MAX_BLOCK_MODIFICATIONS` 面积上限、
   `hasChunksAt`、`isDebug`）**保持在调用线程**——实测这些不碰 `getCurrentWorldData()`，不必投递；
2. 真正的拷贝体抽成 `cloneInOwningRegion(...)`，整体用 `AwaitableDispatch.dispatch`
   投递到**目标位置所在区域的拥有者**，命令**立即返回占位值**（与上游 `FillCommand` 的
   `moonrise$loadChunksAsync(...) { … } return 0` 同构）；
3. 调用方本来就是拥有者时（同区域命令方块）**内联执行**，异常照常传播给 Brigadier；
4. 投递路径里受检异常不能穿透 `Runnable` ⇒ 用 `sendMessage(source, ex)` 发给命令源（照抄 `FillCommand`）。

"先读源、后写目标"的顺序在单个拷贝体内天然保持；未加载/超限仍是**业务响应**
（`That position is not loaded`），不会退化成内部错误。

### 6.1 已知限制（诚实记录）

- **跨维度 clone**（`clone … from <另一个维度>`）在目标维度的区域线程上读源维度方块，
  会命中 `Level.getCurrentWorldData()` 的 `World mismatch` 检查。本补丁**不做多跳搬运**，
  留待 T4 之后（多跳 = 源区域读→目标区域写，并要处理 `getBlockTicks().copyAreaFrom` 与 `MOVE` 的源侧清除）。
- 该路径**不会静默出错**：异常经 `sendMessage` 变成命令失败消息，不会损坏世界。
