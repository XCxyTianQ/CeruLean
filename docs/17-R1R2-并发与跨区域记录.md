## 1. R2：clone 两跳（跨区域 + 跨维度）——已完成

`0017`。原 `0015` 把拷贝体整体投递到**目标维度**的区域线程，而拷贝体要读**源维度**的方块
⇒ `Level.getCurrentWorldData()` 抛 `World mismatch`（docs/15 §6.1）。改为**两跳**：

```
hopA（源维度区域拥有者）：读源方块/方块实体 + MOVE 的源侧清除 + 抓方块刻快照
hopB（目标维度区域拥有者）：先抓目标侧旧状态（任何写入之前）→ 落盘 → 应用方块刻
```

**顺带修掉一个语义错误**：Folia 下 `ServerLevel.getBlockTicks()` 取的是**按区域划分**的容器
（`ServerLevel.java:2219` → `RegionizedWorldData#getBlockLevelTicks`），而原版写的是
`toDimension.getBlockTicks().copyAreaFrom(fromDimension.getBlockTicks(), from, offset)`
—— from/to 同 level 且跨区域时，`source` 参数其实指向**目标区域自己的**容器
⇒ 源区域里已排定的方块刻**不会被搬过去**（vanilla 单线程下两者同一容器，看不出问题）。
处理：`LevelTicks` 新增 `cerulean$snapshotArea(area)` / `cerulean$scheduleSnapshot(ticks, offset)`，
逐行等价于 `copyAreaFrom` 的上下半段，把"读源"与"写目标"拆到各自区域线程。

验收：探针 43/0，含 overworld↔nether **双向**跨维度真拷断言。

## 2. R1：Scoreboard 跨区域并发——已完成

`0022`。风险面（只读审计）：`Scoreboard` 有 **8 个结构性可变容器**，而且**在放开命令之前就已经被多类线程并发写**：

- **区域 tick 线程**：`ServerPlayer.awardStat/resetStat/awardKillScore/handleTeamKill/updateScoreForCriteria`
  → `forAllObjectives` → `getOrCreatePlayerScore`；`ConversionType`/`Evoker`/`SummonEntityEffect` 的团队变更。
  **`handleTeamKill` 最典型：凶手所在区域线程会写受害者的 `playerScores` 条目**——两个区域线程写同一条目，
  是"并发结构修改"的直接证据，不依赖任何命令。
- **global region tick 线程**：`scoreboard` 命令（RCON/控制台都跑在它上面，docs/15 §3）。
- **存档路径**：`MinecraftServer.saveGlobalData`（自动存档时各区域线程仍在跑）。

两层修复：

1. **结构性安全**：容器换并发实现（`ConcurrentHashMap`；`criteria → objectives` 的 List 换
   `CopyOnWriteArrayList`——它极小、增删稀有、迭代在热路径上；集合类换 `newKeySet()`）。
   `ObjectiveCriteria`/`Objective`/`PlayerTeam` 均未重写 `equals/hashCode` ⇒ CHM 的身份语义与
   `Reference2Object*` 一致。
2. **复合操作原子性**：一把**稀疏锁** `stateLock`，只保护"读-改-写"与多容器复合操作；
   **不上热读路径**（`Entity.getTeam()` 这类每 tick 每实体都调的读仍是 CHM 的无锁读）；
   **通知移到锁外**（分数写入热路径的 `onScoreChanged → broadcastAll` 在释放锁后调用）。
   其中 **`add` 被覆写**：默认 `set(get()+count)` 是两段式，两个区域线程同 `add` 同一条分数会丢更新，
   而 `awardStat` 正是区域线程上的 `add`。
   `ServerScoreboard`：`trackedObjectives` 换并发集合、`dirty` 改 `volatile`、
   `storeToSaveDataIfDirty` 的「判定+快照+清零」进临界区（原两段式会**丢一次存档**）。

顺带修正：`Commands.java` 里此前引用的 `0016-CeruLean-scoreboard-region-safe.patch` **并不存在**
（0016 实为 `data-set-nonblocking`）——该错误引用由只读审计发现，已改指 `0022`。

## 2.2 ★ 一次真实回归：并发容器替换丢掉了「null key 容忍」（issue #1）

**症状**：部署后**任意玩家加入即崩**，而且不是普通组件异常，而是
`Folia Region Scheduler Thread` 上"区域 tick 失败"→ 整服进入关服流程：

```
NPE: Cannot invoke "Object.hashCode()" because "key" is null
  at java.util.concurrent.ConcurrentHashMap.get
  at net.minecraft.world.scores.Scoreboard.getPlayerTeam   ← R1 改的就是这一行
  at net.minecraft.server.players.PlayerList.placeNewPlayer
```

**链条**：

1. `PlayerList.placeNewPlayer:382` 在 `if (false && …)`（Folia 关掉碰撞队伍特性）**之外**读取
   `this.collideRuleTeamName` 并调用 `getPlayerTeam(null)`——该字段只在
   `collisions.enable-player-collisions: false` 时才被初始化，**默认 true ⇒ 恒为 null**；
2. R1 把 `Scoreboard.teamsByName` 从 fastutil `Object2ObjectOpenHashMap` 换成 `ConcurrentHashMap`；
3. **两者对 null key 的语义不同**（`javap -c` 实证）：
   - fastutil：`get(Object)` 首行 `ifnonnull` → null 走专门分支 → **返回 null，不抛**；
   - `ConcurrentHashMap`：`get(null)` → **抛 NPE**。

⇒ 上游（未打 `0022`）在默认配置下**不会崩**；`if (false && …)` 的不对称写法是**先前就存在的潜在脏点**，
被 fastutil 的宽容掩盖，被我们的容器替换引爆。（崩溃日志里"上游 26.3 回归"的判断**不成立**。）

**修复**：`0023` 在三个可空入口恢复 null 容忍（保留并发加固，不回退 `0022`）：
`getObjective(@Nullable String)`（形参本来就标了 `@Nullable`，同类潜在雷）、`getPlayerTeam`、`getPlayersTeam`
—— 统一 `name == null ? null : map.get(name)`。

**教训（写进纪律）**：

- **换容器前必须核对原容器对 `null` / 相等性 / 迭代语义的契约**，不能只看"是否线程安全"。
  fastutil 的 `*OpenHashMap` 对 null key 宽容，`java.util.concurrent` 的集合不宽容。
- **验收有盲区**：`tools/smoke` 全是 RCON 驱动、**没有真实客户端**，不覆盖"玩家真正加入"这条路径——
  这正是这个 100% 必现的崩溃没被本地验收挡住的原因。该类路径目前只能靠人工起服 + 真客户端加入验证。
- 另一个过程教训：部署产物的版本串写着 `19721c3`，但该提交里 `0022` 还不存在，
  而栈里明确出现 `ConcurrentHashMap.get` ⇒ 那个 jar 是**从含未提交改动的工作树**构建的。
  **发布构建必须在干净的工作树上做**（`git status` 干净再出包）。

## 3. AwaitableDispatch：tick 线程调用方改为快速失败

T3 当时定的"等待不可消除"依然成立（`data get` 的语义要求，docs/15 §5），
但本轮实测抓到了 T3 担心的隐患**真的会发生**：

```
[FoliaWatchdogThread] Global region has not responded in 5.011959219s
Current Thread: Folia Region Scheduler Thread #0   State: TIMED_WAITING
[CeruLean/AwaitableDispatch] 正在阻塞等待区域线程：线程 'Folia Region Scheduler Thread #0'
                             （是区域 tick 线程：true）等待区块 6/0
```

**根因**：Folia 的 EDF 调度器**按需**起线程。当 `/cerulean regions` 报「调度线程 1」时，
global region 与目标 world region **跑在同一个 `Folia Region Scheduler Thread #0` 上**
⇒ 从 global tick 线程投递后再同步等待 = **等自己把队列排空** ⇒ 自锁，并触发 watchdog。
这解释此前所有"冷启动超时"的偶发现象（有时是 2 个线程、有时 1 个）。

**处理**：tick 线程调用方的等待上限降到 **1.5s**（远小于 watchdog 阈值），超时即抛并说明原因；
非 tick 线程仍用 5s。自检新增 `fastFails` 计数（`/cerulean dispatch`）。
**这是有意的行为改变**：宁可快速失败并给出可诊断的错误，也不要把整个 global region 拖停。

## 4. ★ 环境前提（所有同步跨区域读取都受它约束）

> **同步跨区域读取（`data get`、clone 的"真拷"断言等）要求 Folia 调度器有 ≥2 个线程。**
> 线程数 < 2 时 global region 与目标区域共用同一调度线程，同步等待必然自锁。

因此所有相关探针都加了 `require_two_scheduler_threads()` 前提检查：
不满足时**显式打印 SKIP 并 exit 2**，在套件汇总里记作「未验证」——
**既不算通过也不算失败**，不允许用 exit 0 假装通过。
前提检查本身带重试（最多 ~20s），实测它同时起到了"等调度器把线程数涨上来"的预热作用。

## 5. 其它两条实测经验

- **`applyAllPatches` 会瞬时失败**：观测到 2 次 `BUILD FAILED`（补丁其实已应用），
  同一次运行里 `downloadMcManifest` 这类**网络任务**在跑；立刻重跑即 `Applied 0 patches` + `BUILD SUCCESSFUL`。
  与 `docs/14` §2 记的 GitHub 抖动同类。**判据是重跑一次，而不是怀疑补丁**。
- **hmdfs 不支持硬链接**：用 `write` 类工具写新文件会报
  `EPERM: operation not permitted, link ...`（本机 home 在 hmdfs 上）。写新文件请用 shell heredoc。
