# 07 · C2：把区域拓扑接进真实服务端

> 目标（docs/06 §11）：**区域可切分、可查询、可串行 tick**，且**与 vanilla Paper 行为逐项一致**（世界内容仍由 Paper 原样 tick，不引入并发）。
> 原则（docs/06 附二）：**接线方式照上游**（study/folia/notes/11 的施工图），不自己发明。

## 1. 接线：5 处，全部照上游的接法

| # | 上游怎么接 | 我们的改动 | 位置 |
|---|---|---|---|
| 1 | `BaseChunkSystemHooks.onChunkHolderCreate/Delete` → `level.regioniser.addChunk/removeChunk` | `level.ceruleanRegions.addChunk/removeChunk`（**2 行**，拓扑驱动的唯一源头） | `ca/spottedleaf/moonrise/paper/util/BaseChunkSystemHooks.java` |
| 2 | `ServerLevel` 持有区域化器 | `public final CeruLeanRegions ceruleanRegions` + 构造器初始化 | `net/minecraft/server/level/ServerLevel.java` |
| 3 | 每 tick 驱动区域 | 在 `ServerLevel.tick` **末尾**调用 `tickTopology()`（串行拓扑 tick） | 同上 |
| 4 | 诊断命令 | `/cerulean regions`、`/cerulean regionat <x> <z>` 注册进命令调度器 | `net/minecraft/commands/Commands.java` |
| 5 | 区域自有状态 | `RegionData`（C2 极小：拓扑 tick 计数、合并计数、首次 tick 时刻） | `cerulean-regions/` |

补丁：`cerulean-server/minecraft-patches/features/0001-CeruLean-region-topology.patch`（75 行 / **5 hunk** / 3 个文件）。

## 2. 构建接入：源码单一来源，不复制进补丁

我们的类放在仓库根的两个普通目录里，**通过 `sourceSets` 的 `srcDir` 挂进服务端模块**，而不是把源码复制进补丁：

```
regionizer-core/src/main/java    纯 Java 区域化内核（C1；含模型检验，见 regionizer-core/README.md）
cerulean-regions/src/main/java   MC 侧接线与诊断命令（C2）
```

`cerulean-server/build.gradle.kts.patch`（作用于上游 `paper-server/build.gradle.kts`）中新增：

```kotlin
java {
    srcDir("../paper-server/src/main/java"); srcDir("../paper-server/src/generated/java")
    srcDir("../regionizer-core/src/main/java")    // 单一来源，勿复制进补丁
    srcDir("../cerulean-regions/src/main/java")
}
```

**理由**：复制源码会导致"测试测的是 A、构建用的是 B"的经典分裂。`regionizer-core` 的 113 项断言与模型检验必须与进 jar 的代码是同一份。

**踩过的坑（构建文件补丁格式）**：`applyPaperSingleFilePatches` 要求**单文件构建补丁不带 `diff --git` / `index` 头**（带则报 `Invalid context line ... at 1`）；MC 侧的多文件补丁则用标准 git 格式。

## 3. ★ 实测到的三处版本漂移（"不能照抄上游补丁"的实证）

上游补丁是针对 26.2 生成的；26.3 上同样的写法**编译不过**：

| 漂移 | 上游/旧写法 | 26.3 的正确写法 | 证据 |
|---|---|---|---|
| `ChunkPos` 变成 **record** | `holder.getPos().x` / `.z` | `holder.getPos().x()` / `.z()` | `error: x has private access in ChunkPos` |
| 命令权限模型 | `source.hasPermission(2)` | `Commands.hasPermission(Commands.LEVEL_GAMEMASTERS)` | `error: method hasPermission ... cannot be applied to given types`；原版命令（`AdvancementCommands` 等）已改用该写法 |
| 构造器内初始化位置 | 直接放在构造器开头 | **必须放在 `super(...)` 之后** | `error: cannot reference this before supertype constructor has been called` |

> 这三条正好印证了 `reports/` 里的漂移测量：**逐字照抄上游补丁会失败**，必须按 26.3 的实际上下文重接。

## 4. 运行期驱动：串行拓扑 tick，不做并发

`ServerLevel.tick` 末尾调用 `CeruLeanRegions.tickTopology()`：对每个区域执行一次
"`tryMarkTicking` → 计数 → `markNotTicking`"（即 C1 的稳定化：**合并 → 回收死段 → 必要时分裂**）。

- **为什么放在 tick 末尾**：此时本 tick 内由区块系统带来的段增删都已反映，等价于上游"区域每 tick 释放一次"的语义。
- **为什么不改行为**：拓扑 tick 只碰我们自己的数据结构；世界内容、方块/实体/区块的 tick 全由 Paper 原样处理。
- **开销**：每 tick 每区域一次邻域扫描（精确回收语义）。C3 采纳上游的阈值化回收后会显著下降（docs/06 附二采纳清单第 1 条）。

## 5. 线程边界（C2 实际上已经在用并发）

| 调用点 | 线程 |
|---|---|
| `addChunk` / `removeChunk`（来自 `onChunkHolderCreate/Delete`） | **Moonrise 区块系统线程**（池化） |
| `tickTopology` / 诊断命令 | 主线程 |

因此 C1 内核的 `StampedLock` 在 C2 就已在真实并发下被使用（区域可能在"主线程正在 tick 它"的同时被区块线程加段）。
C1 的验证是单线程的，**并发正确性仍属未验证项**——这是 C3 的任务（调度 + 压力测试）。

## 6. 观测手段

```
/cerulean regions              # 每个 world：区域数 / 段数（存活数）/ 区块数 / 最大区域 + 明细 + 回调计数
/cerulean regionat <x> <z>     # 该区块属于哪个区域（非区块坐标，是区块坐标）
```

`/cerulean regions` 的输出中每个区域带 `拓扑 tick N`，可用于确认"串行拓扑 tick 真的覆盖到了该区域"。
