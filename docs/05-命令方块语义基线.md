# 05 · 命令方块语义基线（源码级 + 实测）

> 这份文档是 **Phase 2 区域化移植的对照基准**：区域化版本必须逐条复现这里的行为，
> 或者明确、有记录地偏离。所有条目都来自本地 materialize 的 Minecraft 源码
> （`cerulean-server/src/minecraft/java/...`，已应用 Paper 补丁）与实测（CeruLean 26.3 服务端）。

## 1. 源码级规则（可直接引用行号）

| # | 规则 | 出处 |
|---|---|---|
| S1 | 命令方块被红石供电时：**若 automatic（Always Active）或模式为 SEQUENCE（链式），则不调度 tick** —— 即链式方块**不响应红石** | `world/level/block/CommandBlock.java:70-73` |
| S2 | 非 automatic 且非 SEQUENCE 的方块（脉冲型）供电时 → `markConditionMet()` + `scheduleTick(pos, this, 1)` | `CommandBlock.java:75-76` |
| S3 | tick 时按模式分派：`AUTO` 分支每 tick 执行并按需重排 tick；`REDSTONE` 分支只在 `wasConditionMet` 时执行一次 | `CommandBlock.java:88-105` |
| S4 | 执行完命令后调用 `executeChain(level, pos, FACING)`，沿 **FACING 方向**逐格推进 | `CommandBlock.java:118, 179-208` |
| S5 | **链传播的关键门槛**：只有当链节点 `isPowered() \|\| isAutomatic()` 时才 `performCommand`，否则跳过（仍继续推进方向） | `CommandBlock.java:194` |
| S6 | 链传播时若某节点 `performCommand` 返回 false（命令失败）→ **break**，链在此中断 | `CommandBlock.java:196-199` |
| S7 | 链长度受游戏规则 `MAX_COMMAND_SEQUENCE_LENGTH` 限制，超限记 warning | `CommandBlock.java:182, 210-213` |
| S8 | 链方块通过 `new CommandBlock(true, ...)` 构造（automatic 初值 true） | `world/level/block/Blocks.java:3838-3841` |
| S9 | 但 `CommandBlockEntity.loadAdditional` 用 **`getBooleanOr("auto", false)`** 读取 —— NBT 里没有 `auto` 就会被置为 **false** | `world/level/block/entity/CommandBlockEntity.java:84, 93` |
| S10 | 方块实体默认值：`DEFAULT_POWERED/DEFAULT_CONDITION_MET/DEFAULT_AUTOMATIC = false` | `CommandBlockEntity.java:22-24` |

**S8 + S9 合起来是本次最有价值的发现**：链方块"天生 automatic"，但只要经过一次 NBT 加载
（例如 `setblock ... {Command:"..."}` 不带 `auto`），就会被**显式改成 non-automatic**；
再叠加 S5 的门槛，链节点就不会执行。这在真实玩法里通常被"放置时自动带上 auto"掩盖，
但在脚本/命令方块注入场景下是极易踩的坑——**区域化移植时必须保持这套语义完全一致**。

## 2. 实测记录（CeruLean 26.3，2026-10-12）

| 实验 | 配置 | 结果 |
|---|---|---|
| 脉冲方块 + 红石上升沿 | `command_block[facing=up]{Command:"setblock ..."}`，下方放/撤红石块 | ✅ 执行（`impulse_redstone_trigger` PASS） |
| always-active 脉冲 | `auto:1b` 放置后不供电 | 👁 **自行执行了一次** |
| 链传播 A（facing 正方向） | 脉冲(facing=up) + 上方 2 个链方块（无 auto） | ❌ 0/2 链节点执行 |
| 链传播 B（全 auto） | 同上但三个方块都带 `auto:1b`（`data get block ... auto` 确认 = `1b`） | ❌ 0/2 链节点执行 |
| 链传播 C/D（水平 east / west） | 脉冲 + 顺/逆 FACING 两个方向各一条链 | ❌ 0/2 链节点执行 |
| 链传播 E/F（两侧对称 + auto） | 脉冲两侧各放一条 auto 链 | ❌ 0/2 链节点执行 |

**结论（如实记录）**：用 `setblock` 合成出来的链式命令方块，在上述所有配置下都**未被触发**，
而脉冲方块正常执行。这说明"链传播"还依赖 S1–S10 之外的状态（例如 `conditionMet` 的簿记、
或交互式放置才建立的某个状态），**当前尚未定位到确切条件**。

处理方式：冒烟用例 `chain_executes_in_order` 因此**标记为 OBSERVED（只记录、不判定）**，
而不是把一个未验证的期望写成 FAIL。定位真实触发条件是 Phase 2 之前要做掉的事——
因为区域化下"命令方块链跨 region 的执行顺序"正是 AzureBranches 那 9 个类要解决的问题。

## 3. 对 Phase 2 的意义

1. 区域化改动如果触碰 `CommandBlock.executeChain` / `CommandBlockEntity` 的
   powered/auto/conditionMet 状态机，**必须**用同一套基线用例回归；
2. S6（失败即中断）与 S7（链长上限）在多区域场景下会变成"跨 region 的中断判定"，
   这是最容易产生语义漂移的两点，建议单独建用例；
3. S9 说明"注入型命令方块"与"玩家放置的命令方块"在状态初始化上并不等价——
   区划化测试如果只用 setblock 搭建场景，会得到与真实玩法不同的结论。
