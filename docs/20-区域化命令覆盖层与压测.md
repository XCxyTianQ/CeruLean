# 20 · 区域化命令覆盖层与压力测试

> 2026-10-18。分支 `main`。前置：`docs/19`（OCC/EXP6Plus 移植）。

## 1. 为什么不是"照搬 upstream 的整文件覆盖"

AzureBranches 用 `azurepatches-src/**`（17 个**26.1.2 全文件快照**）+ `azurepatches-new/**`（7 个新类）
来做命令区域化。直接把这 17 个文件覆盖到 26.3 上，等于把 26.1.2 的所有细节一起带进来，
漂移面不可控（26.3 的 `register(dispatcher, context)` 签名、`NbtPathArgument`、`CommandBuildContext`
都变了）。本仓库采用**实测驱动**的路线：

1. 先**只恢复注册**（`0031`）；
2. 用 `tools/smoke/region_commands_probe.py` 在**两种上下文**下逐条实测
   （RCON = 全局区域 tick 线程；链内 = 目标区域 tick 线程）；
3. **只补真的坏了的那几条**，其余保持 vanilla 26.3 实现。

## 3. 两个真故障的根因

### 3.1 `/loot spawn`：`getCurrentWorldData()` 为 null

```
NPE: Cannot read field "captureDrops" because ServerLevel.getCurrentWorldData() is null
  at ServerLevel.addEntity(ServerLevel.java:1781)
  at LootCommand.lambda$dropInWorld$0(LootCommand.java:383)
```

掉落物的生成是"往世界里 `addFreshEntity`"，必须在**该位置所属区域**的线程上做。
`0031` 用 `RegionCommandExecutor.onBlock(level, pos, ...)` 把 `dropInWorld` 与
`blockDistribute`（容器写入）都包上；链内同区域时会内联，不产生额外跳转。

> 已知降级：从全局线程调用时走的是 `RegionCommandExecutor` 的**阻塞版**，会打印
> `blocking a tick/region thread` 性能告警。upstream 的 LootCommand 覆盖层同样用阻塞版
> （`onBlock`/`onBlockRegion`/`onEntity`），属已知路径，不是错误。

### 3.2 `/reload`：在 tick 线程上阻塞会**打死整个全局区域**

```
Region #-1 ... failed to tick: java.lang.UnsupportedOperationException
  at MinecraftServer.pollTask(MinecraftServer.java:1566)
  at BlockableEventLoop.managedBlock(BlockableEventLoop.java:191)
  at MinecraftServer.reloadResources(MinecraftServer.java:2488)
  at ReloadCommand.reloadPacks(ReloadCommand.java:19)
```

这不是"命令报错"，而是**整服停摆**（`RegionShutdownThread` 随即关服）。
`0031` 在 `reloadResources` 加了守卫：`isSameThread() && !TickThread.isTickThread()` 才阻塞。

但守卫只解决"不炸"，不解决"能重载"：把重载派发到全局 tick 后，资源重载内部
`SimpleReloadInstance` 用 `wait()` 等待，在 tick 线程上直接抛
`UnsupportedOperationException`。正解是**在非 tick 线程跑重载、只把全局状态变更放回全局 tick**，
需要改 `SimpleReloadInstance` 的等待方式 —— 与本轮主题无关，故 `/reload`、`/datapack` 保留
Folia 默认（不注册），原因写在 `Commands.java` 的注释里。

### 3.3 `/spreadplayers`

实测炸两处：`Level.getBlockState → getCurrentWorldData()` NPE（算 Y 轴落点）与
`Entity.teleport → "Must use teleportAsync while in region threading"`。
正解要把整条命令改成 async 传送 + 逐位置区域派发（upstream 是 378 行覆盖），同样留作后续。

## 4. 压力测试

`tools/smoke/command_stress_probe.py`：4 条并列命令方块链（x=4/12/20/28，每条 8 块，内含
`setblock`/`loot spawn`/`tag add·remove`/`scoreboard set`/`get`）+ 主循环穿插 RCON 侧
`/tag`、`/team`、`/loot`、`/scoreboard`、`/data` 命令，跑 N 轮后检查：

- 服务器仍存活；
- OCC 计数器合理（**耗尽 = 0**，通过 > 0）；
- 日志里**没有未捕获异常**（只忽略三条已知噪声：oshi 的 OS 探测、超平坦 worldgen、
  `/loot` 的阻塞桥性能告警）。

8 轮 × 4 链的实测：**4 通过 / 0 失败**，32 次链触发、0 重试、0 耗尽、0 异常。

> 踩坑记录：RCON 客户端是"读到超时才返回"，`wait` 直接等于每次调用的挂钟成本。
> 第一版探针用 `wait=3.0`，8 轮跑了一个多小时还没完；降到 0.25s 后 ~4.5 分钟跑完。

## 5.1 Build 3：三条暂缓命令已修好（`0032`）

上一版把 `/reload`、`/datapack`、`/spreadplayers` 暂缓注册。Build 3 逐条修掉了：

### `/reload`、`/datapack`

真正原因不是 `wait()`，而是 **`SimpleReloadInstance` 的 barrier 用 `mainThreadExecutor.execute(...)` 推进**，
而 `loadResources(..., this.executor, this)` 传的 `mainThreadExecutor` 是 **MinecraftServer 自己**
——它继承自 blockable event loop，Folia 上那个队列**没有任何线程会 drain**（tick 线程上调用还会直接抛）。

修法：`MinecraftServer` 增加 `globalTickExecutor`（把任务投递到 `RegionizedServer.addTask` 的 `Executor`），
并把它作为 `loadResources` 的 `mainThreadExecutor`；启动早期退化为 `Util.backgroundExecutor()`。
pack 仓库变更仍在全局 tick 上做，`managedBlock` 守卫保证 tick 线程不阻塞。

判据（可观测）：日志里 `Loaded N advancements` 每次重载多一次。
实测连续两次 `/reload`：`advancements 1→2`，0 异常，服务器不关停。

### `/spreadplayers`

两处：候选落点计算（`getSpawnY`/`isSafe`）读方块在区域线程外 NPE；`entity.teleportTo` 抛
"Must use teleportAsync while in region threading"。

修法：新增 `spreadPlayersDispatch(...)`，把**整条命令派发到中心位置所属区域**的 tick 线程
（`onBlockRegionAsync`，命令立即返回 1，失败经 `runOnSource` 回报）；传送改为
`getBukkitEntity().teleportAsync(Location, TeleportCause.COMMAND)`。

判据（看效果不收回显）：实体位置真的变了。
实测：僵尸 `(4.5, 64.0, 8.5)` → `(2.5, -60.0, 1.5)`。

**已知限制**：`maxRange` 跨多个区域时，候选位置的方块读仍发生在中心区域线程上；
严格应逐位置派发（upstream 的 378 行覆盖层也只处理了传送 Y，从控制台跑同样会 NPE）。

### 实测

命令矩阵探针：**16 通过 / 0 失败**（此前 12 通过 + 3 项 SKIP）。

## 5.2 `/loot` 的阻塞桥改为非阻塞派发（`0034`）

上一版 `/loot spawn` 用 `RegionCommandExecutor.onBlock(...)`（阻塞桥，内部 2 秒上限）。
回归套件在机器负载偏高时出现 `cross-region command timed out` —— 不是功能错误，而是
**阻塞桥对负载敏感**，而且从 tick 线程阻塞本身就是反模式（还会打性能告警）。

改为 `onBlockAsync(...)`，并把 `usedItems.track(drop)` 提前到**派发之前**：
命令的成功消息由 `CommandResponseTracker(usedItems)` 决定，等异步回调里再记账会误报"没有物品"。
实体生成延后到目标区域的下一个 tick，玩家无感。
